「我们想自己部署一个大模型」——这句话背后通常是一串没人算过的数字：显存够不够、能同时服务几个人、一张卡一秒钟能吐多少 token、为什么 7B 的模型塞进 24G 的卡里却只能跑一个人。

AI Infra 的大部分工作，本质上就是把这笔账算清楚，再让每一块显存、每一份带宽都别闲着。这篇文章按「算账 → 找瓶颈 → 选引擎 → 定容量」的顺序走一遍。

## 一、先把显存账本摊开

一次推理占用的显存只有三块，加起来才是你真正需要的那张卡：

公式先放这里，后面全是它的展开：

```
显存 = 模型权重 + KV Cache × 并发序列数 + 临时 workspace
```

### 1.1 权重：参数量 × 每参数字节数

| 精度 | 每参数字节 | 7B 实占 | 70B 实占 | 备注 |
| --- | --- | --- | --- | --- |
| FP32 | 4 | 28 GB | 280 GB | 训练/对齐用，推理少见 |
| BF16 / FP16 | 2 | 14 GB | 140 GB | 推理的默认基线 |
| INT8（W8A8） | 1 | 7 GB | 70 GB | 精度损失小，需校准 |
| INT4（AWQ/GPTQ） | ~0.5 | 3.5–4.5 GB | 35–45 GB | 有 group scale，比理论值大一点 |

两个容易踩的细节：

一是**量化不是除以 2 这么干净**。AWQ 用 group-wise 量化，每 128 个权重存一组 scale 和 zero，实际体积大约是 INT4 的 1.05–1.15 倍。上面 7B 写 3.5 GB 是理论值，落到磁盘上通常 4.1–4.3 GB。

二是**加载时要留余量**。模型从磁盘读进显存的过程中会有临时峰值，`--gpu-memory-utilization 0.95` 这种配置在权重加载阶段就可能直接 OOM。

### 1.2 KV Cache：真正吃显存的那位

自回归解码时，每个已生成的 token 都要保留它每一层的 Key 和 Value，否则下一个 token 得把前文全部重算一遍。每个 token 的 KV 占用是：

```
每 token 字节数 = 2 × 层数 × KV 头数 × head_dim × 每元素字节数
```

以 Llama-3-8B 为例：32 层、8 个 KV 头（GQA）、head_dim 128、FP16：

```
2 × 32 × 8 × 128 × 2 = 131,072 字节 = 128 KiB / token
```

也就是说，一条 8K 上下文的会话，光 KV cache 就要 8,192 × 128 KiB = **1 GiB**。

这就是为什么 24 GB 卡跑 7B（FP16 占 14 GB）只剩 10 GB：扣掉 workspace，只够 7–8 条 8K 会话。**并发不是由算力决定的，是由 KV cache 决定的**。

GQA 是这里最关键的一次优化。Llama-3-8B 的 32 个注意力头共用 8 组 KV，KV 体积直接降到 MHA 的 1/4。换成 MHA，同一张卡只能撑 2 条 8K 会话。

### 1.3 Workspace：那 10% 别省

CUDA kernel 的临时缓冲、attention 的中间结果、CUDA Graph 的捕获空间、pytorch 的缓存分配器都会占。

实践经验值：给权重 + KV 之外留 8%–15%。vLLM 用 `--gpu-memory-utilization 0.90` 就是这个意思——它把 90% 显存划给自己，剩下的留给上下文切换和碎片。

碎片是隐形成本。连续几十轮不同长度的请求之后，显存里会散落小空洞，长请求可能明明总量够却申请不到。这就是 PagedAttention 要解决的问题（后面讲）。

## 二、瓶颈在哪：算力还是带宽

大模型推理分两个阶段，它们的性能瓶颈完全不同：

| 阶段 | 干什么 | 瓶颈 | 关键指标 |
| --- | --- | --- | --- |
| Prefill | 一次性处理整个 prompt | 算力（矩阵乘法密集） | TTFT（首 token 延迟） |
| Decode | 一个 token 一个 token 往外吐 | 显存带宽（每步都要读全部权重） | TPOT（每 token 时间） |

Decode 阶段的算法非常朴素：每生成一个 token，都要把整个模型的权重从 HBM 读进 SM 算一遍。所以它的上限由带宽决定，跟算力几乎无关：

```
单序列解码速度上限 ≈ 显存带宽 / 权重体积
```

7B FP16（14 GB 权重）跑在两张常见卡上：

| 卡 | 带宽 | 理论上限 | 实测（batch=1） |
| --- | --- | --- | --- |
| A100 80G | 2.0 TB/s | 约 143 token/s | 90–110 token/s |
| H100 SXM | 3.35 TB/s | 约 240 token/s | 160–200 token/s |

实测打七折是正常的：kernel 启动开销、量化反量化、采样逻辑、调度开销都要摊进去。

这个结论带来两个直接的工程决策：

**第一，批处理几乎免费。** batch=1 时权重只被读了一次就为了产出 1 个 token；batch=32 时同样的一次读取产出 32 个 token，显存带宽被摊薄 32 倍，总吞吐能上去十几倍。代价是每条序列的 KV 都要单独占显存。

**第二，量化对解码的收益远大于对 prefill 的收益。** Decode 是带宽瓶颈，权重从 2 字节变 1 字节，读取量减半，速度接近翻倍。这也是为什么消费级卡上 INT4 量化是刚需。

## 三、推理引擎怎么选

自己用 `transformers` + `model.generate()` 写个循环，在单用户演示里没问题，一旦并发就崩：显存按最大长度预分配、请求之间不能插队、一条长请求能把所有短请求堵死。生产环境基本都用专门的推理引擎。

| 引擎 | 强项 | 适合场景 | 注意 |
| --- | --- | --- | --- |
| **vLLM** | PagedAttention、连续批处理、生态最全 | 通用自托管，OpenAI 兼容接口 | 版本迭代快，参数经常改名 |
| **SGLang** | RadixAttention 前缀共享、结构化输出快 | 多轮对话、大量共享 system prompt | 生态略窄，文档相对少 |
| **TensorRT-LLM** | 极致性能、内核融合 | 固定模型、固定形态的线上服务 | 构建编译成本高，改模型要重编 |
| **llama.cpp** | CPU/Metal 可跑、GGUF 生态 | 边缘设备、Mac、单机试用 | 高并发不是它的赛道 |
| **Ollama** | 一条命令拉起，体验极好 | 本地开发、内网小工具 | 生产并发和可观测性偏弱 |

选型的一句话版本：**要快且省心选 vLLM，前缀复用极多选 SGLang，要把硬件榨干且模型固定选 TensorRT-LLM，要在没有 GPU 的机器上跑选 llama.cpp。**

## 四、四个真正改变了吞吐的技术

### 4.1 PagedAttention：把 KV cache 当虚拟内存管

传统实现按 `max_seq_len` 给每条请求预分配一块连续显存。三条请求、每条 8K，就锁死 3 GiB，哪怕实际只用了 500 token。实测显存浪费常在 60%–80%。

PagedAttention 借用操作系统的分页思路：把 KV cache 切成固定大小的 block（vLLM 默认 16 个 token 一块），用 block table 做逻辑到物理的映射。效果是：

- 按需分配，显存浪费降到 4% 以下
- block 可以不连续，碎片问题基本消失
- 相同前缀的请求能共享物理 block，直接省显存

这就是 vLLM 能在同样硬件上把并发提高 2–4 倍的原因。

### 4.2 连续批处理（continuous batching）

静态批处理要等一批请求齐了才开跑，跑完一起返回，快请求被慢请求拖死。连续批处理在**每个解码步**重新组批：谁结束了就把位置让出来，队列里的新请求立刻补进去。

对用户来说，短请求不再排队等长请求；对机器来说，batch 始终是满的。这是吞吐提升的第二大来源。

### 4.3 Chunked Prefill：别让长 prompt 卡住所有人

一个 32K 的 prompt 做 prefill 会占满 GPU 几十毫秒到上百毫秒，这期间所有正在解码的请求全部停摆，表现为「打字突然卡住」。

Chunked prefill 把长 prompt 切成几块，和 decode 请求混在同一批里算。代价是长 prompt 的 TTFT 略微变长，收益是所有人的 TPOT 都稳了。

### 4.4 前缀缓存（prefix caching）

多轮对话里，每一轮都要把前面的历史重新 prefill 一遍。而 system prompt、历史消息这些前缀是完全一样的。

前缀缓存把已经算过的 KV block 按内容哈希存起来，命中就直接复用。一轮 10K 上下文的多轮对话，第二轮开始能省掉绝大部分 prefill 计算，TTFT 从几百毫秒掉到几十毫秒。

vLLM 的开关：`--enable-prefix-caching`。

### 4.5 投机解码（speculative decoding）

用一个小模型（或同一模型的多 token 头）先猜出 4–8 个 token，大模型一次前向并行验证，猜对的部分直接采纳。

它的收益高度依赖任务：代码补全、格式化输出这类「可预测」的内容能提速 2–3 倍，自由创作类可能只有 1.1 倍，因为猜错要回滚。而且它会额外吃显存（草稿模型 + 更长的验证 buffer），并发高的时候反而可能拖累吞吐。

**结论：并发低的场景值得开，追求总吞吐的场景通常不值得。**

## 五、从 QPS 反推要买几张卡

这是最实用的一节。给定业务指标，反推硬件：

```
需要的同时在线会话数 N = QPS × 平均会话时长
每条会话 KV = 上下文长度 × 每 token KV
KV 总量 = N × 每条会话 KV
```

举个具体的例子。假设：

- 模型 7B，AWQ INT4，权重约 4 GB
- 平均上下文 4K，每 token 128 KiB → 每会话 512 MiB
- 目标 30 路并发
- 单卡 24 GB（如 4090 / L4）

算账：

```
可用 KV 显存 = 24 × 0.90 − 4（权重）− 2（workspace）≈ 15.6 GB
KV 需求     = 30 × 0.5 GB = 15 GB
```

刚好卡在边缘——这意味着 24 GB 卡做 30 路 4K 并发是极限值，没有余量给流量峰值。要么把上下文压到 3K，要么上 48 GB 卡，要么两台。

再看吞吐。7B INT4 在 L4（300 GB/s 带宽）上，权重 4 GB：

```
单序列上限 ≈ 300 / 4 = 75 token/s
batch=16 时总吞吐 ≈ 500–700 token/s（受算力限制，非线性增长）
```

按人均输出 300 token 算，单卡约能支撑 1.7–2.3 请求/秒的解码吞吐。这就是容量规划的实际输入。

:::tip
把上下文长度当成最重要的成本参数。同样是 30 路并发，上下文从 8K 压到 2K，KV 需求直接降到 1/4，一张卡能顶四张卡用。绝大多数业务其实不需要 8K 的对话历史——**裁剪历史比买卡便宜得多**。
:::

## 六、多卡：TP、PP、EP 怎么选

单卡装不下了，只有三条路：

| 方式 | 切什么 | 通信量 | 适用 |
| --- | --- | --- | --- |
| **TP**（张量并行） | 每层的权重矩阵按列/行切 | 每层两次 all-reduce，量最大 | 单机内，NVLink 优先 |
| **PP**（流水并行） | 按层切，前几层在卡 A、后几层在卡 B | 只在层边界传激活，量小 | 跨机、卡间只有 PCIe |
| **EP**（专家并行） | MoE 的专家分到不同卡 | all-to-all，取决于路由 | MoE 模型（Mixtral、DeepSeek） |

实践中的取舍很明确：

- **同机多卡优先 TP**，因为 all-reduce 走 NVLink（900 GB/s）而不是 PCIe（64 GB/s）。TP=8 在单机 8 卡上是常规操作。
- **跨机只能用 PP**，通信量小，代价是流水线气泡——前面卡在算、后面卡在等。微批（micro-batch）越多，气泡越小。
- **MoE 模型看 EP**。DeepSeek 这类模型总参数巨大但激活很少，EP 能让每张卡只装一部分专家，比 TP 切稠密层高效得多。

一个常被忽略的点：**TP 会让延迟变差**。TP=4 意味着每层要多两次 all-reduce 等待，decode 的 TPOT 可能从 20 ms 涨到 30 ms。用多卡换的是显存和吞吐，不是单请求速度。

## 七、容器化落地

vLLM 官方镜像就够了，关键是参数：

```bash
docker run -d --gpus all --ipc=host --name llm \
  -p 8000:8000 \
  -v /data/models:/models \
  vllm/vllm-openai:latest \
  --model /models/Qwen2.5-7B-Instruct-AWQ \
  --quantization awq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 64 \
  --enable-prefix-caching \
  --served-model-name chat
```

几个参数的含义和踩坑点：

- `--ipc=host`：vLLM 用共享内存传张量，不给 host IPC 会报 `Bus error` 或直接卡死。
- `--max-model-len`：**不要设成模型的最大值**。设 8192 时每条请求最多占 1 GiB KV；设成 32768 会直接吃掉 4 GiB/条，并发瞬间塌掉。
- `--max-num-seqs`：同时处理的序列上限，是控制延迟和吞吐平衡的旋钮。
- `--gpu-memory-utilization`：0.90 比较稳，0.95 在长上下文场景容易 OOM。

健康检查别用 `/v1/models`——它在权重加载完之前就返回了。vLLM 提供 `/health`，权重加载完成后才 200：

```yaml
startupProbe:
  httpGet: { path: /health, port: 8000 }
  failureThreshold: 60
  periodSeconds: 5      # 大模型加载要 2-5 分钟，给足时间
livenessProbe:
  httpGet: { path: /health, port: 8000 }
  periodSeconds: 15
```

在 Kubernetes 上还有两个坑：

**一是滚动更新会杀掉长连接。** 一个 SSE 流式请求可能持续几十秒，`terminationGracePeriodSeconds` 默认 30 秒，正好卡在中间。要设到 120–300，并且在 preStop 里先摘流量再等一会儿。

**二是 GPU 节点不能随便驱逐。** 大模型加载要几分钟，被驱逐一次就是几分钟的服务真空。要么给 Pod 加 `priorityClass`，要么干脆用裸机 + systemd 托管。

## 八、上线后盯哪些指标

| 指标 | 含义 | 健康范围（参考） |
| --- | --- | --- |
| TTFT P95 | 首 token 延迟 | < 800 ms |
| TPOT P95 | 每 token 时间 | < 50 ms（约 20 token/s） |
| 队列等待时间 | 请求在 scheduler 里排队多久 | < 100 ms |
| KV cache 使用率 | 显存里 KV 的占用比例 | 60%–85%，长期 > 95% 该扩了 |
| running / waiting | 正在跑 vs 在排队的请求数 | waiting 长期 > 0 说明容量不足 |
| tokens/s per GPU | 单卡吞吐 | 用来算单位成本 |
| GPU SM 占用 | 算力利用率 | decode 阶段低是正常的 |

最后一条特别容易被误判：**decode 阶段 SM 利用率只有 10%–30% 是正常的**，因为瓶颈在带宽不在算力。看到 SM 占用低就以为机器闲着的，往往会做出错误的扩容决策——要看 KV 使用率和 waiting 队列。

## 九、踩坑清单

按「我被坑过的顺序」排列：

1. **上下文长度设太大**，并发直接塌。先算 KV，再定 `--max-model-len`。
2. **没开 prefix caching**，多轮对话白白重算前缀，TTFT 高得莫名其妙。
3. **健康检查探到未就绪的 Pod**，流量打进来全是 503。用 `/health` 加 `startupProbe`。
4. **忘了 `--ipc=host`**，容器起来几秒后静默死掉。
5. **量化模型与引擎不匹配**，AWQ 权重用 GPTQ 的加载器，报一堆 shape 错误。
6. **多卡用 PCIe 做 TP**，跨 NUMA 通信把扩展比压到 0.6，四张卡不如两张。
7. **没限并发就上线**，一个爬虫把队列打满，所有真实用户看到的是超时。
8. **只监控 GPU 利用率不监控队列**，扩容永远慢半拍。

## 小结

把上面所有内容压成四句话：

- 显存 = 权重 + KV + workspace，**并发上限由 KV 决定，不是算力**。
- Prefill 吃算力，Decode 吃带宽，**decode 的批处理几乎免费**。
- 吞吐的三大来源是 PagedAttention、连续批处理、前缀缓存；投机解码只在低并发时划算。
- 容量规划从 QPS 和上下文长度入手，**先调上下文，再考虑加卡**。

AI Infra 没有魔法，只有账。账算对了，剩下的都是把配置调到位。
